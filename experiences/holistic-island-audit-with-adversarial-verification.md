# Holistic Island Audit with Adversarial Verification

## 🎯 چالش / Challenge

یک سیستم شخصی/داخلی طی ده‌ها سشن رشد کرده و صاحبش دیگر تصویر کلی ندارد: «یه چیزهایی
پراکنده‌کاری شده، یه جاهایی جزیره‌ای کار می‌کنن، نمی‌دونم چی کم داره.» بررسی دستی
همهٔ فایل‌ها در یک context جا نمی‌شود؛ بررسی سطحی هم ادعاهای غلط تولید می‌کند («X به
Y وصل نیست» در حالی که وصل است). لازم است: پوشش کامل + ادعاهای اثبات‌شده + خروجی
اولویت‌بندی‌شده برای مالک غیرفنی.

## 💡 راه‌حل / Solution

خط لولهٔ چهارمرحله‌ای با ایجنت‌های موازی:

1. **Map (خواننده‌های حوزه‌ای):** سیستم را به ۶–۹ حوزهٔ عمودی تقسیم کن (دامنه‌های
   کسب‌وکار + سه حوزهٔ افقی که همیشه فراموش می‌شوند: «ستون اتوماسیون: چه چیزی واقعاً
   خودش اجرا می‌شود؟»، «معماری اطلاعات فرانت: از کجا می‌شود به کجا رسید؟»، «حافظهٔ
   پروژه: لاگ‌ها/TODOها/وعده‌های اجرانشده»). به هر خواننده «چشم‌انداز مالک» را به‌عنوان
   متر بده و خروجی ساخت‌یافته بخواه: works / integrations / islands / gaps /
   duplications / quick_wins با سقف تعداد و الزام «evidence = مسیر فایل و خط».
2. **Merge (ادغام و رتبه‌بندی):** یک ایجنت، ادعاهای هم‌معنا از حوزه‌های مختلف را ادغام
   می‌کند (دو حوزه معمولاً یک جزیره را از دو سمت گزارش می‌کنند — این خودش سیگنال
   اهمیت است)، و بر اساس اثر روی چشم‌انداز مالک، N ادعای برتر را برمی‌گرداند.
3. **Verify (راستی‌آزمایی خصمانه):** برای هر ادعا یک ایجنت مستقل با دستور «تلاش کن رد
   کنی: grep کن اتصالِ ادعاشده-به-نبودن واقعاً هیچ‌جا نیست؟ mount/wiring را چک کن».
   خروجی: refuted/verdict/corrected. بخش `corrected` طلاست — بیشتر ادعاها «درست ولی
   نادقیق»اند و نسخهٔ دقیق‌شده اعتبار گزارش نهایی را می‌سازد.
4. **Critique (منتقد کامل‌بودن):** یک ایجنت آخر با سؤال «این ممیزی چه چیزی را ندید؟»
   و تلنگرهای مشخص: امنیت/دسترسی، backup، محدودیت‌های زیرساخت (sleep/free-tier)،
   هزینهٔ AI، موبایل، جستجو، خودتوضیحی محصول. تجربه نشان داد مهم‌ترین یافتهٔ کل ممیزی
   (دادهٔ باز روی اینترنت) از همین مرحله درآمد، نه از خواننده‌های حوزه‌ای.

## 🧪 نمونه کد (Anonymized)

```javascript
// workflow pseudo-script
const domains = await parallel(DOMAINS.map(d => () =>
  agent(`${VISION}\nYOUR DOMAIN: ${d.scope}\n${LIMITS}`, { schema: FINDINGS })))
const top = await agent(`dedup semantically + rank vs owner vision:\n${JSON.stringify(domains)}`,
  { schema: RANKED })          // barrier is justified: dedup needs ALL domains
const verified = await parallel(top.claims.map(c => () =>
  agent(`Try to REFUTE against the repo: ${c.claim}\ncited: ${c.evidence}`,
    { schema: VERDICT }).then(v => ({ ...c, v }))))
const critic = await agent(`What did this audit MISS? Probe: security, backup,
  infra sleep, AI cost, mobile, search, self-explanation. Verify before reporting.`,
  { schema: MISSED })
```

## ⚠️ نکات حیاتی / Pitfalls

- **بدون مرحلهٔ Verify گزارش نده.** خواننده‌های حوزه‌ای مرتب «unmounted/مرده» می‌گویند
  برای چیزی که mount است ولی مصرف‌کننده ندارد — تمایز «کد مرده» با «جزیرهٔ محصول»
  فقط در راستی‌آزمایی درمی‌آید و همین تمایز، توصیهٔ درمان را عوض می‌کند.
- **سقف تعداد یافته به هر خواننده بده** وگرنه خروجی ادغام‌نشدنی می‌شود؛ رتبه‌بندی را به
  متر واحد (چشم‌انداز مالک) گره بزن نه به سلیقهٔ ایجنت.
- **«evidence = مسیر فایل:خط» را اجباری کن** — ادعای بدون مسیر، قابل راستی‌آزمایی نیست
  و باید دور ریخته شود.
- **حوزه‌های افقی را جدا کن.** اگر فقط عمودی (دامنه‌ای) تقسیم کنی، هیچ‌کس «کدام jobها
  واقعاً در production اجرا می‌شوند» و «از ناوبری به کجا نمی‌شود رسید» را نمی‌بیند —
  دو مورد از پرتکرارترین ریشه‌های حس «پراکندگی».
- **خروجی منتقد را با کد چک کن** (به خودش هم بگو verify کند) وگرنه سوگیری «حتماً
  چیزی جا افتاده» یافتهٔ جعلی می‌سازد.
- زبان ادعا/اثر را زبان مالک نگه دار و مسیر فایل‌ها را لاتین — گزارش دوزبانه‌ی
  قابل‌خواندن برای مالک و قابل‌اجرا برای توسعه‌دهنده.

## 🔁 چطور در جای دیگر اعمال کنیم / How to Apply Elsewhere

1. چشم‌انداز مالک را در یک پاراگراف بنویس؛ همین متن، متر مشترک همهٔ ایجنت‌ها می‌شود.
2. سیستم را به دامنه‌های عمودی + ۳ برش افقی (اتوماسیون واقعی، ناوبری/IA، حافظه/وعده‌ها)
   تقسیم کن؛ به هر کدام schema ساخت‌یافته با سقف و الزام evidence بده.
3. ادغام معنایی + رتبه‌بندی با متر چشم‌انداز؛ منابع چندگانهٔ یک ادعا را نگه دار.
4. هر ادعای برتر را با یک ایجنت «ردکننده» راستی‌آزمایی کن؛ فیلد corrected را در گزارش
   نهایی به‌جای ادعای خام بنشان.
5. منتقد کامل‌بودن با چک‌لیست نقاط کور استاندارد (امنیت، backup، زیرساخت، هزینه،
   موبایل، جستجو، راهنما) اجرا کن.
6. خروجی را سه‌لایه تحویل بده: (الف) ۲–۳ «بیماری ساختاری» ریشه‌ای، (ب) یافته‌های
   گروه‌بندی‌شده با evidence، (ج) نقشهٔ راه فازبندی‌شده که فاز صفرش ایمنی/اعتماد است.

# ایمنی محتوای ارزشمند مالک — ردیابی کامل مسیرهای تغییر/حذف + دو مهار فوری

**تاریخ:** 2026-07-20
**درخواست مالک:** «لیست‌ها و محتواهایی که از قبل هست و برایم ارزشمند است چه می‌شوند؟ چه
کار می‌شود کرد که نه کم شود نه دستکاری شود؟ اصلاً نمی‌دانم چه چیزهایی نوشته‌ام.»
**روش:** ورک‌فلوی ۶-ایجنته — ۴ فهرست‌بردار موازی محتوا + ۱ ردیاب ایمنی (تمام مسیرهای
UPDATE/DELETE روی جدول‌های محتوایی) + ۱ راستی‌آزمای مستقل برای دو ادعای حیاتی.
**خروجی همراه:** `docs/CONTENT_INVENTORY.md` (دفتر موجودی — «چی دارم و کجاست»).

## ۱) پاسخ کوتاه به مالک

- محتوایت **در git محفوظ است**: نسخهٔ پایهٔ هر ۳۳+۲۲+۸ لیست و هر دو نوشتهٔ بلند، عیناً
  و با گیت‌های ماشینی verbatim در repo ثبت شده و با هر بوت، DB خالی از همین نسخه پر
  می‌شود.
- seedها **ویرایش‌های تو را بازنویسی نمی‌کنند** (fill-empty، نه upsert) — راستی‌آزمایی
  مستقل تأیید کرد.
- اما **دو رفتار برنامه‌ریزی‌شده در startup پیدا شد که می‌توانست محتوای آیندهٔ تو را کم
  کند** (بخش ۲) — هر دو در همین تاریخ مهار و تست شدند.
- ریسک‌های واقعیِ باقی‌مانده (بخش ۴) هیچ‌کدام از جنس seed نیستند: نبود backup، نبود سطل
  زباله، و باز بودن مسیر نوشتنِ ناشناس.

## ۲) دو مهار اعمال‌شده (CHANGE این تاریخ)

### الف) HARD RESET لیست «شخصیت یک مرد الهی» (app/main.py:578-683)
- **قبل:** اگر تعداد آیتم‌ها ≠ ۴۱ یا جای note/header عوض شده بود، کل لیست حذف سخت و از
  seed بازسازی می‌شد — **در هر بوت** (free tier یعنی عملاً هر روز). یعنی اولین آیتمی که
  خودت به این لیست اضافه می‌کردی، شب بعد همراه همهٔ تیک‌ها و ویرایش‌ها می‌پرید. (بلوک
  برای رفع باگ ترتیب نمایش ساخته شده بود و در زمان ساختش لیست هنوز دادهٔ کاربری نداشت.)
- **حالا:** `divine_man_hard_reset_verdict` (در self_improvement_service) فقط وقتی
  اجازهٔ reset می‌دهد که **بدون‌خسارت اثبات شود**: تعداد دقیقاً برابر seed، تک‌تک
  محتواها عیناً از seed، و هیچ آیتمی تیک‌نخورده — یعنی همان حالت باگ اصلی. هر انحرافی
  (آیتم افزوده/حذف‌شده/ویرایش‌شده/تیک‌خورده) ⇒ log + دست‌نزدن به داده. قابلیت حفظ شد
  (rule 2)، فقط شرط مخربش قرنطینه شد — ثبت در REMOVAL_CANDIDATES.
### ب) پاک‌سازی پیشوندی لیست «محاسبه» (self_improvement_service.py:395-425)
- **قبل:** هر ردیفی با شروع «مراقبه:» یا «نکته:» در هر بوت/هر باز کردن لیست حذف سخت
  می‌شد — یعنی یادداشت‌های آیندهٔ خودت با این شروع‌های طبیعی فارسی، بی‌صدا «گم» می‌شدند.
- **حالا:** حذف پیشوندی فقط وقتی فعال است که ردیف‌های exact-match قدیمی (نشانهٔ وضعیت
  پیش-مهاجرت) هنوز در لیست باشند؛ بعد از پایان مهاجرت، ردیف پیشوندی = یادداشت مالک و
  هرگز لمس نمی‌شود.
- **تست‌ها:** ۲ تست جدید (گارد verdict با ۵ سناریو؛ بقای یادداشت‌های «نکته:/مراقبه:»
  مالک پس از مهاجرت) + ۲۲/۲۲ تست ماژول سبز؛ تست‌های قدیمی پاک‌سازی مهاجرتی دست‌نخورده
  پاس می‌شوند.

## ۳) نقشهٔ کامل مسیرهای تغییر/حذف محتوا (ردیابی‌شده و راستی‌آزمایی‌شده)

| مسیر | چه می‌کند | کی اجرا می‌شود | ریسک (پس از مهارها) |
|---|---|---|---|
| seedهای todo/PD/نوشته‌ها | فقط جدول/لیست خالی را پر می‌کنند | هر بوت | کم — ویرایش‌ها امن؛ فقط لیستِ صددرصد خالی‌شده دوباره seed می‌شود |
| HARD RESET مرد الهی | بازسازی ترتیب لیست | هر بوت، **فقط حالت بدون‌خسارت** | مهارشده ✅ |
| پاک‌سازی پیشوندی محاسبه | حذف ردیف‌های مهاجرتی | بوت/GET لیست، **فقط پیش-مهاجرت** | مهارشده ✅ |
| catch-up/realign لیست‌های SI | آیتم seed حذف‌شده را برمی‌گرداند؛ آیتم ویرایش‌شده را ته لیست می‌برد و نسخهٔ اصلی را دوباره درج می‌کند | بوت/GET لیست | متوسط — دادهٔ تو حذف نمی‌شود ولی تکرار/جابه‌جایی می‌سازد (پیشنهاد ۵ در بخش ۵) |
| بازنویسی description لیست‌های SI | توضیح canonical را برمی‌گرداند | بوت/GET لیست | متوسط — ویرایش توضیح این چند لیست پایدار نمی‌ماند |
| DELETE آیتم/نوشته/لیست | حذف سخت؛ بدون سطل زباله؛ CASCADE زیرآیتم‌ها با والد | کلیک/درخواست API | بالا — بدون undo (پیشنهاد ۳) |
| PUT نوشته | بدنهٔ ۶۳هزارکاراکتری را بی‌نسخه بازنویسی می‌کند | درخواست API | بالا — بدون تاریخچه (پیشنهاد ۳ و ۴) |
| نوشتن/حذف ناشناس | با user_id=NULL روی seedها، بدون توکن هم ممکن است؛ **حتی REQUIRE_AUTH=true این روت‌ها را نمی‌بندد** (get_optional_user_id) | همیشه (URL عمومی) | بالا (پیشنهاد ۲) |
| merge/dedup | فقط دستی؛ لیست مبدأ آرشیو نرم، آیتم‌ها منتقل | دکمهٔ دستی | کم |
| sync-from-file | آیتم‌های غایب از فایل را از لیست unlink می‌کند (یتیم، نه حذف) | آپلود دستی | متوسط — بدون تأیید دومرحله‌ای |
| telegram compose (update) | description آیتم موجود را با ادغام AI بازنویسی می‌کند | پیام تلگرام | متوسط — قول no-loss در مسیر AI تضمین کد ندارد |
| html.escape در ذخیره | متن با & < > " در هر ویرایش escape انباشتی می‌گیرد | هر PUT/PATCH | متوسط — خرابی تدریجی بی‌صدا (پیشنهاد ۶) |
| حذف لیست | آیتم‌ها را نمی‌کشد (فقط عضویت) | درخواست API | ضربه‌گیر مفید ✅ |

**راستی‌آزمایی مستقل:** (الف) رفتار seedها «فقط-وقتی-خالی» تأیید شد — حذف بخشی از
آیتم‌ها زنده نمی‌شوند مگر لیست کاملاً خالی شود؛ نوشته per-title است (حذف نوشتهٔ seed در
بوت بعد برمی‌گردد، ویرایش با حفظ عنوان محفوظ است). (ب) نوشتن ناشناس روی هر سه مسیر
lists/todo-items/writings عملاً باز است و متغیر REQUIRE_AUTH روی این روت‌ها بی‌اثر است.

## ۴) ریسک‌های باز (به ترتیب اولویت)

1. **نبود backup** — تنها نسخهٔ تغییرات پس از seed (و کل CRM/چک‌این/مالی جاری) در
   Postgres رایگان Render است.
2. **نوشتن ناشناس** — هر کسی با URL می‌تواند بدون توکن حذف/ویرایش کند (بخش ۳).
3. **نبود سطل زباله/نسخه‌داری** — یک کلیک اشتباه = نابودی برگشت‌ناپذیر.
4. رفتار catch-up/realign لیست‌های SI (تکرار/جابه‌جایی برای آیتم‌های ویرایش‌شده).
5. html.escape انباشتی در لایهٔ ذخیره.

## ۵) پیشنهادها (نیازمند تصمیم/اقدام مالک — اجرا نشده)

1. **Backup روزانهٔ خودکار** (فاز ۰ نقشهٔ راه): pg_dump شبانه → آپلود Drive با زیرساخت
   موجود + قاعدهٔ توجه «backup عقب افتاد».
2. **بستن نوشتنِ ناشناس** با الگوی dual-path (خواندن lenient بماند، DELETE/PUT/PATCH به
   get_required_user_id مهاجرت کند) — هماهنگ با task 9a5a3b4d؛ چون فرانت فعلی بدون
   توکن کار می‌کند، باید همراه فلوی login انجام شود، لذا تصمیم مالک لازم است.
3. **soft-delete + سطل زباله** برای TodoItem و PersonalWriting (ستون deleted_at +
   endpoint بازیابی + پاک‌سازی ۳۰روزه) و هدایت UI حذف لیست به is_archived موجود.
4. **نگه‌داشتن مقدار قبلی در activity log** (payload_before) برای update/delete آیتم و
   نوشته — undo عملی تا رسیدن backup.
5. **realign/catch-up فقط insert-if-missing** شود و از مسیر GET خارج شود (فقط startup)؛
   حذف عمدی مالک محترم شمرده شود.
6. **html.escape از لایهٔ ذخیره حذف** شود (escape فقط هنگام رندر) + تست رفت‌وبرگشت.
7. نسخهٔ اصلی فایل‌های منبع (Word/Excel/Forms/PDF) که در repo نیستند، یک‌بار در Drive
   آرشیو شوند.

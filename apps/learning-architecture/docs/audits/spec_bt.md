# مشخصات «بک‌تست کارخانه معرفت‌شناسی» (برای نویسندگان محتوا)

## زمینه
کارخانه معرفت‌شناسی (جزوه مصباح؛ ایستگاه‌ها در app/epi_st_*.js؛ متن جزوه در epi/ch/*.txt؛ مشخصات قبلی در epi/spec_epi.md) حالا یک «لوله‌کشی قطعی» می‌گیرد، الگوگرفته از صفحه ترید کوانتومی یک سامانه معاملاتی:
- **تونل** = هر ایستگاه (خانواده اصول جزوه). **باکس** = هر قاعده جزوه روی آن ایستگاه. **وزن** = شدت اثر قاعده (فقط شدت تنظیم می‌شود، نه ماهیت و جهت).
- هر پرونده (رخداد واقعی، مثال جزوه، سناریوی ساختگی، مسئله حل‌شده) به «ویژگی»‌هایی رمزگذاری می‌شود (فهرست ثابت در `app/epi_feat.js` — حتماً بخوانید). موتور بدون هوش مصنوعی پرونده را از قواعد عبور می‌دهد: برای هر تصدیق «سقف اعتبار موجه» و «پرچم‌های خطا» می‌سازد و نخستین نقطه شکست را نشان می‌دهد.
- **بک‌تست**: پرونده‌هایی که سرنوشتشان معلوم است از موتور عبور می‌کنند. پرونده سالم (فرایند معرفتی واقعاً درست، نه شانسی) باید بی‌پرچم عبور کند؛ پرونده شکست‌خورده باید در همان ایستگاهی پرچم بخورد که شکست واقعاً آنجا رخ داد. «دادگاه» با آماره‌های سخت‌گیرانه (درون‌نمونه/برون‌نمونه، دو دوره زمانی، کران پایین ویلسون، کنترل مثبت و منفی) حکم می‌دهد. خطاها کالبدشکافی می‌شوند: اشتباه جزوه؟ بدفهمی سازنده؟ خطای رمزگذاری؟ خلأ؟
- هوش مصنوعی فقط سازنده و دستیار جمع‌آوری است؛ داخل لوله‌کشی نیست.

## زبان شرط (COND) — دقیقاً همین
```
{ f: "کلید ویژگی", eq: مقدار } | { f, ne: مقدار } | { f, in: [مقادیر] } | { f, is: true|false } |
{ f, gt: عدد } | { f, gte } | { f, lt } | { f, lte } |
{ all: [COND, ...] } | { any: [COND, ...] } | { not: COND }
```
- کلیدها و مقادیر enum باید **دقیقاً** همان‌های `app/epi_feat.js` باشند (حتی نیم‌فاصله).
- اگر ویژگی در پرونده نیامده (نامعلوم)، هر شرط اتمی روی آن false است (حتی `ne` و `is:false`). برای «نامعلوم» قاعده ننویسید مگر واقعاً لازم باشد (`{f:"narrator", eq:"نامعلوم"}` مجاز است چون مقدار enum است).

## قاعده (EPI_RULES)
```js
window.EPI_RULES = window.EPI_RULES || [];
window.EPI_RULES.push({
  id: "r_xxx",                 // یکتا، لاتین
  book: "mesbah",              // جزوه مبدأ
  st: "st_istiqra",            // ایستگاهی که قاعده در آن است (= تونل)
  sec: ["s50", "s40"],          // بخش‌های پشتوانه جزوه
  fa: "نام کوتاه قاعده",
  stmt: "حکم قاعده دقیقاً طبق جزوه (یک یا دو جمله)",
  when: COND,
  eff: "cap" | "flag",
  cap: 80,                     // فقط برای cap: سقف اعتبار موجه (۰ تا ۱۰۰) وقتی قاعده با وزن کامل فعال است
  err: "نام خطایی که این قاعده می‌گیرد (برای کالبدشکافی)",
  fix: "مسیر درست: اگر کنشگر ... می‌کرد، ... (عملیاتی و کوتاه)",
  basis: "booklet" | "system", // آیا خود حکم از جزوه است، یا صورت‌بندی/عدد آن افزوده سامانه است
  note: "اگر عدد سقف یا بخشی از شرط افزوده سامانه است، اینجا بگویید چرا این عدد (جزوه فقط ترتیب کیفی می‌دهد)"
});
```
معناشناسی موتور (برای نوشتن درست قواعد):
- سقف هر تصدیق از ۱۰۰ شروع می‌شود. هر قاعده `cap` فعال، سقف را به `100 − w·(100 − cap)` محدود می‌کند (w وزن قاعده، پیش‌فرض ۱، تنظیم‌پذیر بین ۰ و ۱). سقف نهایی = کمینه همه. قاعده‌ها **فقط کاهنده‌اند**؛ قاعده افزاینده ننویسید (مثلاً متواتر و نص هیچ سقفی نمی‌گیرد و خودبه‌خود ۱۰۰ می‌ماند).
- **بیش‌اطمینانی**: موتور خودش (قاعده داخلی، لازم نیست بنویسید) اگر `conf > سقف + تحمل` باشد، تصدیق را در ایستگاهِ قاعده‌ای که سقف را تعیین کرده پرچم می‌زند (مبنا: s40 و s53). پس قاعده‌های cap باید ایستگاه درست را داشته باشند.
- هر قاعده `flag` فعال، امتیاز خطای ایستگاهش را `w` بالا می‌برد؛ ایستگاه با امتیاز ≥ آستانه (پیش‌فرض ۰٫۵) پرچم می‌خورد. flag برای خطاهایی است که مستقل از میزان اطمینان، خطا هستند (مغالطه کل و جزء، خلط صدق اخلاقی، خودشکنی، پیش‌زمینه نابایسته، ترک تحقیق ممکن پیش از عمل پرخطر، نادیده گرفتن شاهد ناسازگار…).
- پرونده «سالم» است اگر هیچ ایستگاهی پرچم نخورد. «نخستین نقطه شکست» = اولین ایستگاه پرچم‌خورده به ترتیب `EPI_PIPE`.

## پرونده (EPI_CASES)
```js
window.EPI_CASES = window.EPI_CASES || [];
window.EPI_CASES.push({
  id: "cs_xxx", kind: "real" | "booklet" | "problem",
  title: "عنوان", dom: "علم" | "پزشکی" | "ریاضی" | "مالی و بانکی" | "بازار و معامله" | "تاریخ و سیاست" | "فناوری و مهندسی" | "حقوق و قضا" | "رسانه و خبر" | "زندگی روزمره" | "دین" | "فلسفه",
  year: 1847,                  // سال رخداد (برای تقسیم دو دوره زمانی؛ مثال جزوه: سال تقریبی یا 0)
  grp: "semmelweis",           // گروه استقلال: پرونده‌هایی که از یک رخداد ریشه می‌گیرند یک گروه‌اند
  src: ["منبع قابل‌راستی‌آزمایی: عنوان مدخل/کتاب/مقاله"],
  story: "روایت دقیق و بی‌طرفانه رخداد (۳ تا ۸ جمله)؛ فقط واقعیت‌های مستند",
  actor: "چه کسی بر پایه چه تصدیقی داوری یا عمل کرد",
  claims: [{ id: "k1", txt: "متن تصدیقِ داوری‌شده", role: "اصلی" | "مقدمه", f: { /* ویژگی‌ها از epi_feat.js */ }, truth: true | false | null }],
  truth: {
    ok: true | false,          // آیا فرایند معرفتی سالم بود (نه صرفاً نتیجه درست)؟ موفقیت شانسی = ok:false
    fail: ["st_xxx"],          // ایستگاه(های) واقعی شکست (برای ok:false)؛ خالی برای ok:true
    why: "تحلیل: دقیقاً کجا و چرا فرایند معرفتی شکست خورد یا سالم ماند، با ارجاع به ملاک جزوه (sNN)",
    right: "مسیر درست: اگر ... آنگاه ... (برای شکست‌ها)؛ برای سالم‌ها: کدام ملاک‌ها رعایت شد"
  },
  status: "approved", by: "seed"
});
```
قواعد رمزگذاری:
- فقط ویژگی‌هایی را بگذارید که از منابع روشن است؛ بقیه را نگذارید (نامعلوم). `conf` = اطمینانی که کنشگر واقعاً نشان داد (از رفتار و سخنش؛ تقریب صادقانه).
- برچسب حقیقت (`truth.ok` و `fail`) را مستقل از قواعد بنویسید: از تحلیل خود رخداد با ملاک‌های جزوه، نه از اینکه موتور چه خواهد گفت. هدف آزمودن موتور است؛ برچسب‌گذاری به سود موتور تقلب است.
- پرونده‌های سالم واقعی (فرایند درست به نتیجه درست رسید) به همان اندازه شکست‌ها مهم‌اند (آزمون سلامت سامانه). نسبت تقریبی ۴۰٪ سالم، ۶۰٪ شکست.
- موفقیت شانسی (فرایند معیوب، نتیجه درست) = `ok:false` با توضیح.
- منابع: فقط رخدادهای مشهور و مستند. اگر جزئیاتی مطمئن نیست، ننویسید.
